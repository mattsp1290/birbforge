Runtime choice

Why Temporal and Pydantic AI are the first combination to prove.

Researched November 5, 2026. The owner approved self-hosted Temporal and Pydantic AI as the first Crew runtime to validate. These choices authorize readiness planning, not implementation. No factory account integrations, workers, or restart behavior have been live-tested.

Accepted direction and remaining proof#

Use one self-hosted Temporal service for factory coordination and durable coworker execution, with PostgreSQL persistence. Keep Forge's interface and CopilotKit OSS runtime in TypeScript. Evaluate Python with Pydantic AI as the preferred Crew implementation because it has documented AG-UI and Temporal integrations. Retain TypeScript with the pi SDK as the alternative if the end-to-end proof shows lower integration or account-access cost.

This recommendation prioritizes existing integrations over using one language everywhere. It does not replace Codex, Claude Code, or pi as coding tools. Cloud authors and coding harnesses remain separately invoked execution backends. Crew's chief of staff uses constrained factory tools to coordinate them. Crew is the first implementation repository. Each repository gets its own poteto-mode owner handoff.

Why Temporal#

Our durable unit is a delivery lifecycle: author a change, wait for review, reserve staging, verify it, wait for human input where required, merge, and observe deployment health. A model conversation is only part of that lifecycle.

Temporal workers poll queues and can run outside the service. That lets the same workflow coordinate k3s workloads and the existing Mac execution paths. Long waits need not keep a model generating or an agent process busy. Worker model

Use existing SDK primitives for workflows, activities, timers, cancellation, messaging and versioning. The custom work is expressing delivery policy and reconciling external effects. Temporal does not supply our PR approval model or guarantee exactly-once deployments. TypeScript SDK

Self-hosting requires backups, schema upgrades, monitoring and restricted network access. Deploy a sustained-workload service, not a development server. Keep infrastructure definitions in Birbhomes. PostgreSQL application records and Temporal persistence must have separate ownership and migrations even if they share an operated PostgreSQL installation. Deployment guidance, persistence

Pi already exposes persistent sessions, custom tools and lifecycle events. Its session-settled signal matters: a lower-level run-end event may precede automatic recovery or queued work. A correct AG-UI bridge must preserve those semantics. Pi SDK

Pydantic AI provides an AG-UI adapter and a Temporal durability capability. Its documented workflow-stream integration can carry live agent events without adding a separate message broker. These are available building blocks, not proof that our phone reconnect and cross-device history already work. A direct HTTP agent invocation is not automatically a durable background workflow. AG-UI, Temporal

Its existing harness also includes skills, repository context, context-management and instrumentation capabilities. Adopt only those we need. This makes it a credible existing-runtime choice rather than an invitation to recreate pi in Python. Datadog remains the observability destination; a new hosted observability product is not part of this recommendation. Harness capabilities

The standalone CopilotKit runtime stays TypeScript even if Crew is Python. That runtime can connect to an AG-UI agent without Intelligence. Do not confuse a Python agent backend with CopilotKit's Python runtime, which has a different service dependency. CopilotKit OSS boundary

Where pi-durable fits#

Pi-durable documents persisted conversations, model/tool execution and process recovery, but explicitly marks its API experimental. It is a distinct harness, not simply a persistence switch on the coding-agent SDK. Do not initially stack it under Temporal without a specific benefit and clear ownership for retries, cancel, tools and state. Revisit it if it removes more code than it adds. Pi-durable

A restarted workflow must reconnect to existing external work where possible. It must not resubmit an entire coding task just because a polling activity died. Model/tool work belongs in supported durable activities or framework adapters, not arbitrary nondeterministic calls in workflow code. Coordinate one active writer per session. Stream disconnection is separate from cancellation.

Reuse the enrolled Mac#

The owner confirms that the Mac is already joined to the k3s setup. Birbhomes documents a Linux guest for cluster/container work and a native macOS runner for Apple tooling, with existing lifecycle and network gates. Respect both paths. Do not introduce an always-on Temporal worker that bypasses those gates.

First evaluate dispatching native checks through the existing runner. If a dedicated Temporal activity worker removes meaningful integration work, it must be supervised by the same lifecycle controls. The choice is still open; neither approach is implemented or qualified here. Do not copy private host, account or network coordinates into these public docs.

Proof needed before implementation commitment#

  1. A coworker uses an eligible existing account to call one authorized factory tool, with no accidental API billing or custom token broker.
  2. The run streams through AG-UI to phone and browser; disconnecting both leaves work running, and reconnecting recovers coherent state.
  3. Restart a worker during a tool call. Recover or explicitly reconcile the outcome without duplicate external action.
  4. Pause for a durable human-input request and resolve it from another client. Forge later proves revision-bound approvals through the phone interface.
  5. Recover finalized conversation history after process restart.
  6. In the later Verify integration milestone, dispatch a real check through the existing Mac path. Respect its lifecycle gates and preserve the shared-staging reservation through interruption.

Framework provider documentation is not proof of our accounts' entitlement or unattended operation. Pydantic AI documents subscription-related integrations, so do not dismiss it as necessarily requiring paid API keys; verify the selected path against provider documentation and the actual deployment before adoption. Pydantic provider documentation

Temporal is the selected shared engine. The first implementation milestone validates Pydantic AI using the bounded proof above. Do not build both stacks or a general-purpose runtime abstraction. A local Temporal development service is appropriate for this isolated proof. Birbhomes owns the subsequent sustained k3s deployment. The Birbparty acceptance milestone still requires deployed k3s verification.
